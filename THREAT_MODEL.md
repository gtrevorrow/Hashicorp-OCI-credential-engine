# Threat Model

When analyzing and deploying a security-sensitive component like this HashiCorp Credential Engine, defining the threat model—which encompasses both **trust boundaries** and specific **attack vectors**—is critical.

---

## 1. Trust Boundaries

Trust boundaries define the architectural perimeter across which data or execution context must be validated because it transitions between entities of differing trust levels.

### The Plugin JWKS Publication Boundary (Self-Minted & Brokered Re-Issue)
The plugin's published JWKS is a core trust boundary whenever OCI is configured to trust JWTs signed by this plugin's self-mint signing key.
*   **The Architecture:** In built-in self-mint mode, and in brokered mode after the plugin validates and re-issues an incoming external JWT, OCI validates the plugin-issued JWT against public keys published from the plugin's self-mint signing key. The `oci/jwks` export endpoint currently requires `subject_token_self_mint_enabled=true`; brokered-only deployments that rely on plugin re-issue must account for JWKS publication as part of their signing-key setup.
*   **The Boundary Operator:** Whoever controls publication of that JWKS document, or rotation of the underlying self-mint signing key, can affect what OCI will trust as plugin-issued identity.

### Vault System Identity-Token Boundary (Plugin-Issued Mode)
When `subject_token` is omitted and `enable_plugin_issued_subject_token=true`, the default callback first asks Vault's system view to generate a Vault identity token before falling back to built-in self-minting.
*   **The Architecture:** In this mode, the plugin may exchange a Vault-issued identity token with OCI instead of a token signed by the plugin's self-mint key. The trust boundary is therefore Vault's identity-token issuer, its configured issuer/audience behavior, and the Vault runtime identity context available to the plugin.
*   **The Boundary Operator:** Vault Administrators and Vault Auth Method configuration.

### The Upstream Brokered Verification Boundary (Brokered Mode)
Brokered mode introduces a second trust surface: how the plugin validates the external JWT before re-issuing it.
*   **The Architecture:** The plugin can trust brokered tokens using OIDC discovery, a JWKS URL, inline JWKS JSON, or inline public keys. When `brokered_subject_token_trust_type=oidc_discovery` or `jwks_url`, the plugin fetches verification material over HTTP(S) at request time.
*   **The Boundary Operator:** Identity Provider Administrators and whoever controls the configured discovery/JWKS endpoint or the inline trust material stored in Vault.

### Vault Configuration API Boundary (`oci/config` & `oci/role/*`)
The plugin relies heavily on its internal definitions to dynamically generate claims and handle trust.
*   **The Architecture:** Any Vault user or token possessing `update` capabilities on the `oci/config` path or `oci/role/*` paths has administrative control over the trust engine. They can alter OCI OAuth client credentials, self-mint issuer and signing key material, brokered trust sources and allowed algorithms/audiences, `subject_token_role_mappings`, `brokered_subject_token_claim_mappings`, and role-level `self_mint_custom_claims`.
*   **The Boundary Operator:** Vault Administrators.

### The Upstream External IdP Boundary (Brokered Mode)
In Brokered mode, Vault accepts a `subject_token` generated by an external Identity Provider (e.g., Azure AD, Auth0, Okta, Kubernetes), validates it, relies on its claims, and re-mints a token for OCI.
*   **The Architecture:** The plugin inherently extends its trust to the external IdP. Vault validates the incoming token's signature, issuer, allowed audience, and time-based claims, then maps selected claims into a new plugin-issued JWT for OCI.
*   **The Boundary Operator:** Identity Provider Administrators.

### Vault Runtime Identity Boundary (Built-In Self-Minted Mode)
When the plugin self-mints without an external JWT, it bases its trust entirely on the caller's Vault identity (e.g., `vault_entity_id`, aliases, and groups).
*   **The Architecture:** The plugin trusts the Vault core engine to verify *how* the workload authenticates to Vault. 
*   **The Boundary Operator:** The Vault Auth Method configuration.

### Stored Secret Material Boundary (`oci/config`)
The plugin stores long-lived secrets in backend storage that directly affect its trust posture.
*   **The Architecture:** `oci/config` stores the OCI OAuth `client_secret`, and stores or auto-generates the RSA private key used to sign self-minted and brokered re-issued JWTs. Compromise of that storage or write access to that path is equivalent to compromise of the plugin's issuance authority.
*   **The Boundary Operator:** Vault Administrators and Vault's storage protection model.

### Response Disclosure Boundary (Debug Claims Echo)
The plugin has an optional debug feature that changes what data is returned from `/oci/exchange`.
*   **The Architecture:** When `debug_return_resolved_subject_token_claims=true`, the plugin includes decoded claims from the resolved subject token in exchange responses, including some error paths. This can expose identity attributes that would otherwise remain internal to Vault or the upstream token.
*   **The Boundary Operator:** Vault Administrators.

### Transport and Caller Memory Boundary (The Returned Exchange Private Key)
When the caller omits `public_key`, the plugin generates an RSA private/public keypair on the fly for the OCI exchange. OCI receives the public key, and Vault returns the generated `private_key` to the caller.
*   **The Architecture:** Once that `private_key` traverses the network and lands in the client's memory or on disk, it leaves the Vault security boundary entirely. 
*   **The Boundary Operator:** The Calling Client / Workload.

## 2. Attack Vectors & Mitigations

While the trust boundaries define the "locks on the doors", the attack vectors describe how an active adversary might try to pick those locks.

### A. Token Replay Attack
*   **The Attack:** An adversary intercepts a legitimate JWT as it travels from the user to Vault, or steals a recently used JWT from application logs, and attempts to exchange it again for a fresh OCI session token.
*   **The Mitigation:** In brokered mode, the plugin validates signature, `iss`, allowed `aud`, and time-based claims (`exp` required, `nbf` and `iat` when present). This narrows acceptance to tokens within the configured trust window, but it is **not** a one-time-use replay defense: the plugin does not persist `jti`, nonce, or token-use state. In direct pass-through mode, replay resistance depends on Vault TLS, secure logging practices, short upstream token lifetimes, and any replay protections enforced by OCI or the upstream IdP.

### B. Privilege Escalation via Upstream Claim Manipulation
*   **The Attack:** In Brokered Mode, the plugin uses `brokered_subject_token_claim_mappings` to map claims (like `department: {{ claims.department }}`). If an attacker finds a way to edit their own profile in the upstream IdP (e.g., Azure AD) and changes their department to `admin`, they can trick Vault into issuing a highly privileged OCI token.
*   **The Mitigation:** Vault administrators must ensure that mapped claims originate only from strictly controlled, non-user-editable fields in the upstream IdP. 

### C. The "Confused Deputy" (Stolen Vault Token)
*   **The Attack:** An attacker compromises a developer's machine and steals their active `~/.vault-token`. Since the developer has self-mint access via `oci/exchange/developer`, the attacker uses the stolen Vault token to self-mint OCI credentials, hoping to pivot into the cloud infrastructure.
*   **The Mitigation:** The blast radius can be contained if OCI trust is anchored to strong Vault-derived claims such as `vault_entity_id`, alias metadata, or tightly controlled group membership, and if Vault ACLs restrict which `oci/exchange` paths the token can call. If OCI trust instead relies on weaker context such as `vault_display_name`, or if broad exchange access is granted, the impact grows. Vault administrators can revoke the stolen Vault token to stop minting of new OCI sessions, but already-issued OCI tokens continue until they expire.

### D. JWKS / Discovery Endpoint Substitution
*   **The Attack:** An attacker hijacks or substitutes the URL used either by OCI to fetch the plugin's published JWKS, or by the plugin to fetch brokered verification keys via OIDC discovery or `brokered_subject_token_jwks_url`.
*   **The Mitigation:** Use HTTPS endpoints wherever possible, protect DNS and hosting control, and prefer inline trust material (`jwks_json` or `public_keys`) when you want to remove runtime dependency on a remote verification endpoint. Note that the current implementation accepts `http://` as well as `https://` for `brokered_subject_token_jwks_url`, and OIDC discovery uses the configured `brokered_subject_token_issuer` URL without independently enforcing HTTPS. Operators must treat any non-HTTPS brokered trust source as explicitly weaker.

### E. Exposed Generated Exchange Private Key
*   **The Attack:** A client workload requests an OCI exchange without providing a public key. The plugin generates one and returns the private key. The workload writes this private key to a shared `/tmp` directory or exposes it in CI logs, where it is stolen by an attacker.
*   **The Mitigation:** Callers should ideally pre-generate their *own* key pairs securely in-memory, and pass only the `public_key` to Vault's `/exchange` endpoint. That way, the private key never traverses the network and Vault doesn't handle the private material for the session.

### F. Sensitive Claim Disclosure via Debug Responses
*   **The Attack:** An operator enables `debug_return_resolved_subject_token_claims` in an environment where exchange responses are visible to callers, logs, or support tooling. An attacker then learns brokered or self-minted JWT claims that were only meant for internal trust decisions.
*   **The Mitigation:** Keep `debug_return_resolved_subject_token_claims=false` outside development and treat any environment that enables it as handling additional sensitive identity data.

### G. Configuration Secret Compromise
*   **The Attack:** An attacker gains raw plugin-storage access and extracts the OCI OAuth client secret or self-mint signing key, or gains privileged `oci/config` write capabilities and replaces OCI OAuth credentials, the self-mint signing key, brokered trust roots, or claim-mapping configuration. Normal Vault API reads of `oci/config` expose trust configuration such as issuers, audiences, JWKS URLs/JSON, public keys, and claim mappings, but intentionally omit `client_secret` and `subject_token_self_mint_private_key`.
*   **The Mitigation:** Protect `oci/config` as a high-value administrative path, rely on Vault storage protections and audit controls, and rotate OCI client credentials or the self-mint signing key after any suspected compromise.
