# Threat Model

When analyzing and deploying a security-sensitive component like this HashiCorp Credential Engine, defining the threat model—which encompasses both **trust boundaries** and specific **attack vectors**—is critical.

---

## 1. Trust Boundaries

Trust boundaries define the architectural perimeter across which data or execution context must be validated because it transitions between entities of differing trust levels.

### The Plugin JWKS Publication Boundary (Self-Minted & Brokered Re-Issue)
The plugin's published JWKS is a core trust boundary whenever OCI is configured to trust JWTs signed by this plugin's self-mint signing key.
*   **The Architecture:** In built-in self-mint mode, and in brokered mode after the plugin validates and re-issues an incoming external JWT, OCI validates the plugin-issued JWT against public keys published from the plugin's self-mint signing key. The `oci/jwks` export endpoint currently requires `subject_token_self_mint_enabled=true`; brokered-only deployments that rely on plugin re-issue must account for JWKS publication as part of their signing-key setup.
*   **The Boundary Operator:** Whoever controls publication of that JWKS document, or rotation of the underlying self-mint signing key, can affect what OCI will trust as plugin-issued identity.

### Vault System Identity-Token Boundary (Plugin-Issued Mode)
When `subject_token` is omitted and `enable_plugin_issued_subject_token=true`, the default callback first asks Vault's system view to generate a Vault identity token before falling back to built-in self-minting.
*   **The Architecture:** In this mode, the plugin may exchange a Vault-issued identity token with OCI instead of a token signed by the plugin's self-mint key. The trust boundary is therefore Vault's identity-token issuer, its configured issuer/audience behavior, and the Vault runtime identity context available to the plugin.
*   **The Boundary Operator:** Vault Administrators and Vault Auth Method configuration.

### The Upstream Brokered Verification Boundary (Brokered Mode)
Brokered mode introduces a second trust surface: how the plugin validates the external JWT before re-issuing it.
*   **The Architecture:** The plugin can trust brokered tokens using OIDC discovery, a JWKS URL, inline JWKS JSON, or inline public keys. When `brokered_subject_token_trust_type=oidc_discovery` or `jwks_url`, the plugin retrieves bounded verification material over HTTPS and caches one key set per mount for five minutes. HTTP is allowed only through explicit loopback debug configuration.
*   **The Boundary Operator:** Identity Provider Administrators and whoever controls the configured discovery/JWKS endpoint or the inline trust material stored in Vault.

### Vault Configuration API Boundary (`oci/config` & `oci/role/*`)
Vault ACLs separate mount-wide configuration authority from administration of individual roles.
*   **Backend Configuration (`oci/config`):** Write access controls OCI OAuth client credentials, exchange modes, self-mint issuer and signing key material, brokered trust sources and allowed algorithms/audiences, backend TTL policy, `subject_token_role_mappings`, and `brokered_subject_token_claim_mappings`.
*   **Role Administration (`oci/role/<name>`):** Write access controls the permitted role's description, default/maximum TTLs, and `self_mint_custom_claims`. It does not grant access to change OAuth credentials, signing keys, or brokered trust configuration. Role writes remain security-sensitive because custom claims, including operator-defined literals, can influence OCI identity mapping. Protect role administration and workload access to the corresponding exchange paths together.
*   **The Boundary Operators:** Backend configuration administrators and any separately authorized role administrators, within their respective Vault ACL scopes. See [exchange access controls](docs/security.md#access-controls-for-self-mint-and-exchange).

### The Upstream External IdP Boundary (Brokered Mode)
In Brokered mode, Vault accepts a `subject_token` generated by an external Identity Provider (e.g., Azure AD, Auth0, Okta, Kubernetes), validates it, relies on its claims, and re-mints a token for OCI.
*   **The Architecture:** The plugin inherently extends its trust to the external IdP. Vault validates the incoming token's signature, issuer, allowed audience, and time-based claims, then maps selected claims into a new plugin-issued JWT for OCI.
*   **The Boundary Operator:** Identity Provider Administrators.

### Vault Runtime Identity Boundary (Built-In Self-Minted Mode)
When the plugin self-mints without an external JWT, it bases its trust entirely on the caller's Vault identity (e.g., `vault_entity_id`, aliases, and groups).
*   **The Architecture:** The plugin uses the entity and request context supplied by Vault core. Alias attributes are omitted unless an operator configures an auth mount accessor; exactly one linked alias must match. That alias describes a linked identity, not proof of the current login method. Request mount fields describe the OCI secrets engine.
*   **The Boundary Operator:** The Vault Auth Method configuration.

### Stored Secret Material Boundary (`oci/config`)
The plugin stores long-lived secrets in backend storage that directly affect its trust posture.
*   **The Architecture:** `oci/config` stores the OCI OAuth `client_secret`, and stores or auto-generates the RSA private key used to sign self-minted and brokered re-issued JWTs. Compromise of that storage or write access to that path is equivalent to compromise of the plugin's issuance authority.
*   **The Boundary Operator:** Vault Administrators and Vault's storage protection model.

### Response Disclosure Boundary (Debug Claims Echo)
The plugin has an optional debug feature that changes what data is returned from `/oci/exchange`.
*   **The Architecture:** When `debug_return_resolved_subject_token_claims=true`, the plugin includes decoded claims from the resolved subject token in exchange responses, including some error paths. This can expose identity attributes that would otherwise remain internal to Vault or the upstream token.
*   **The Boundary Operator:** Vault Administrators.

### OCI Session Token and Exchange Private-Key Boundary
The returned UPST or RPST binds an OCI principal to the public key supplied during exchange. The client signs OCI API requests with the matching private key and sends the session token in the `keyId` parameter of the `Authorization` signature header. OCI validates the token and uses its embedded public key to verify the request signature. See [session tokens and request signing](docs/usage.md#session-tokens-and-request-signing).
*   **The Architecture:** When the caller omits `public_key`, the plugin generates an RSA keypair and returns the matching `private_key` with the session token. Both reach the caller outside Vault's storage boundary and need protection in transit, memory, files, and logs. When the caller supplies `public_key`, it retains its own private key and Vault returns no private key. This exchange keypair is separate from the issuer signing key used for self-minted or brokered subject JWTs.
*   **The Boundary Operator:** The Calling Client / Workload.

## 2. Attack Vectors & Mitigations

While the trust boundaries define the "locks on the doors", the attack vectors describe how an active adversary might try to pick those locks.

### A. Token Replay Attack
*   **The Attack:** An adversary intercepts a legitimate JWT as it travels from the user to Vault, or steals a recently used JWT from application logs, and attempts to exchange it again for a fresh OCI session token.
*   **The Mitigation:** In brokered mode, the plugin validates signature, `iss`, allowed `aud`, and time-based claims (`exp` required, `nbf` and `iat` when present). This narrows acceptance to tokens within the configured trust window, but it is **not** a one-time-use replay defense: the plugin does not persist `jti`, nonce, or token-use state. In direct pass-through mode, replay resistance depends on Vault TLS, secure logging practices, short upstream token lifetimes, and any replay protections enforced by OCI or the upstream IdP.

### B. Privilege Escalation via Upstream Claim Manipulation
*   **The Attack:** In Brokered Mode, the plugin uses `brokered_subject_token_claim_mappings` to map claims (like `department: {{ claims.department }}`). If an attacker finds a way to edit their own profile in the upstream IdP (e.g., Azure AD) and changes their department to `admin`, they can trick Vault into issuing a highly privileged OCI token.
*   **The Mitigation:** Vault administrators must ensure that mapped claims originate only from strictly controlled, non-user-editable fields in the upstream IdP.

### C. The "Confused Deputy" (Stolen Vault Token)
*   **The Attack:** An attacker compromises a developer's machine and steals their active `~/.vault-token`. Since the developer has self-mint access via `oci/exchange/developer`, the attacker uses the stolen Vault token to self-mint OCI credentials, hoping to pivot into the cloud infrastructure.
*   **The Mitigation:** The blast radius can be contained if OCI trust is anchored to strong Vault-derived claims such as `vault_entity_id`, alias metadata, or tightly controlled group membership, and if Vault ACLs restrict which `oci/exchange` paths the token can call. If OCI trust instead relies on weaker context such as `vault_display_name`, or if broad exchange access is granted, the impact grows. Vault administrators can revoke the stolen Vault token to stop minting of new OCI sessions, but already-issued OCI tokens can remain valid until expiry or OCI-side invalidation.

### D. JWKS / Discovery Endpoint Substitution
*   **The Attack:** An attacker hijacks or substitutes the URL used either by OCI to fetch the plugin's published JWKS, or by the plugin to fetch brokered verification keys via OIDC discovery or `brokered_subject_token_jwks_url`.
*   **Plugin Fetching Upstream Brokered Keys:** The plugin enforces HTTPS, exact discovery issuer matching, an explicit discovered-JWKS origin policy, checked destination IPs, and no redirects or environment proxies. Private and local network destinations are blocked except for explicit loopback debug testing. Documents and key counts are bounded, and signing-key metadata/strength constrain verification. Protect DNS and endpoint administration; use managed inline trust material for private-network IdPs. The plugin's cache entries last five minutes, unknown-key refreshes and failed retries have a 30-second cooldown, and refresh failures fail closed. Removing an upstream key can take up to five minutes to affect this cached verification. `debug_allow_brokered_http=true` permits HTTP only on loopback for local testing and must be disabled in production.
*   **OCI Fetching the Published Plugin JWKS:** Protect the publication account, document write access, DNS, and HTTPS hosting used by the OCI trust configuration. The plugin exports public key material; OCI performs the external retrieval. The plugin's address, redirect, proxy, document-size, and cache controls do not govern that retrieval. Account for OCI's own key discovery and caching behavior when planning signing-key changes or responding to compromise; the plugin's five-minute verification cache does not establish an OCI cache or invalidation deadline. See the [JWKS publication workflow](docs/configuration.md#self-mint-jwks-publication-workflow).

### E. Exposed Generated Exchange Private Key
*   **The Attack:** A client requests an exchange without providing a public key, so the plugin returns the generated private key with the session token. An attacker who obtains that key and its matching session token, for example from a shared `/tmp` response file or CI logs, can sign OCI API requests as the token's principal within its granted permissions. The token alone is insufficient to create new valid signed requests.
*   **The Mitigation:** Callers can generate their own keypair securely and pass only `public_key` to Vault's `/exchange` endpoint, keeping the private key out of the exchange response and Vault's handling. Client-side generation reduces that exposure but still requires protecting the private key and session token on the workload. Protect response transport, client memory and files, and logging or support tooling that can capture credentials. See [using returned credentials](docs/usage.md#using-returned-credentials-with-oci-clients).

### F. Sensitive Claim Disclosure via Debug Responses
*   **The Attack:** An operator enables `debug_return_resolved_subject_token_claims` in an environment where exchange responses are visible to callers, logs, or support tooling. An attacker then learns brokered or self-minted JWT claims that were only meant for internal trust decisions.
*   **The Mitigation:** Keep `debug_return_resolved_subject_token_claims=false` outside controlled troubleshooting. Explicit activation expires after 15 minutes with a persisted deadline, checked again before returning claims. Restarts and unrelated writes do not renew it; legacy flags without deadlines are inactive. Activation and diagnostic use emit warnings without claims. While active, responses still intentionally disclose identity data to callers, including on OCI rejection. Concurrent config changes cannot recall an in-flight request's config snapshot. See [diagnostics](docs/security-logging.md#temporary-claim-diagnostics).

### G. Configuration Secret Compromise
*   **The Attack:** An attacker gains raw plugin-storage access and extracts the OCI OAuth client secret or self-mint signing key, or gains privileged `oci/config` write capabilities and replaces OCI OAuth credentials, the self-mint signing key, brokered trust roots, or claim-mapping configuration. Normal Vault API reads of `oci/config` expose trust configuration such as issuers, audiences, JWKS URLs/JSON, public keys, and claim mappings, but intentionally omit `client_secret` and `subject_token_self_mint_private_key`.
*   **The Mitigation:** Protect `oci/config` as a high-value administrative path, rely on Vault storage protections and audit controls, and replace OCI client credentials or the self-mint signing key after suspected compromise, coordinating external JWKS publication. Automated overlapping signing-key rotation is not implemented.

### H. Direct Role Delegation and Request Schema

Direct `subject_token_role_mappings` intentionally permits a caller with access to bare `/exchange` to obtain a mapped role without named-role ACL access. Mapping reads a decoded payload; OCI authenticates the unchanged JWT during exchange. This is distinct from brokered local verification. Strict exchange validation rejects unknown fields before token processing, including body `role` on the bare route. Removed `allowed_subjects`/`allowed_groups` fields never enforced access; populated legacy roles require explicit cleanup before use.

### I. Alias Misattribution

Automatic first-alias selection has been removed. `subject_token_identity_alias_mount_accessor` makes linked-identity trust explicit and fails issuance on missing or ambiguous matches. A caller authenticating through another alias on the same entity can still receive the selected attributes. OCI rules requiring evidence of a specific current login must not treat those claims as that evidence. Live multi-auth acceptance remains outstanding.

### J. Template Validation and Resource Use

Both mapping modes parse complete templates before data lookup on writes and at runtime. Missing values cannot hide invalid trailing expressions. Templates are limited to 16 KiB and rendered claims to 64 KiB each; these are not aggregate JWT limits. Rendering remains constrained to approved namespaces and fails on missing data, type errors and claim collisions. No general scripting, loops or conditional evaluation is supported.

### K. Development Credential Disclosure

Dev helpers now keep checkout-scoped state and logs owner-only, send secret config through stdin, generate random root tokens, and verify the managed local Vault target. Smoke tests use isolated resources, assert claims without printing token/claim responses, and attempt cleanup and configuration restoration. Vault startup logs can still contain generated credentials; private permissions do not protect them from the same OS user or root. Real Vault/OCI helper acceptance is outstanding. See CONTRIBUTING for upgrade and cleanup limits.

### L. Lease and Deployment Limits

The plugin enforces exchanged-credential TTL ceilings and reports OCI expiry only when the response supplies it. Vault leases are nonrenewable; their expiry or revocation does not make an OCI invalidation call. Local/mock tests do not establish live OCI authorization, Vault ACL enforcement, an edition/version compatibility matrix, FIPS validation, or production-network readiness. Audit devices and safe logging must be configured by the operator.

OCI token-endpoint bodies and descriptions are redacted from client errors. Structured operational events use allowlisted metadata, never token/claim/key values or raw errors. Repeated failure warnings are rate limited and operational logs can be filtered or lost; they are not a complete audit trail. Configure Vault audit devices with sensitive strings HMACed and protect log access/retention. Canary tests include a disposable local Vault and mock OCI endpoint; they do not establish production audit durability or live OCI behavior. See [the logging contract](docs/security-logging.md).
