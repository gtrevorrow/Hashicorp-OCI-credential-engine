# Threat Model

When analyzing and deploying a security-sensitive component like this HashiCorp Credential Engine, defining the threat model—which encompasses both **trust boundaries** and specific **attack vectors**—is critical.

---

## 1. Trust Boundaries

Trust boundaries define the architectural perimeter across which data or execution context must be validated because it transitions between entities of differing trust levels.

### The JWKS Distribution Boundary (Self-Minted & Brokered)
As a primary example, the JWKS endpoint is a massive piece of the trust boundary.
*   **The Architecture:** In self-minted and brokered modes, OCI validates incoming session requests by reaching out to a published URL (e.g., an S3 bucket, GitHub Pages, or an HTTPS server) hosting the Vault plugin's public keys.
*   **The Boundary Operator:** Whoever has `Write` access to the location where the `jwks.json` is published essentially holds the keys to your OCI tenant.

### Vault Configuration API Boundary (`oci/config` & `oci/role/*`)
The plugin relies heavily on its internal definitions to dynamically generate claims and handle trust.
*   **The Architecture:** Any Vault user or token possessing `update` capabilities on the `oci/config` path or `oci/role/*` paths has administrative control over the trust engine. In brokered mode, they can alter claim mappings. If self-minting, they can alter the internal RSA private key.
*   **The Boundary Operator:** Vault Administrators.

### The Upstream External IdP Boundary (Brokered Mode)
In Brokered mode, Vault accepts a `subject_token` generated by an external Identity Provider (e.g., Azure AD, Auth0, Okta, Kubernetes), validates it, relies on its claims, and re-mints a token for OCI.
*   **The Architecture:** The plugin inherently extends its trust to the external IdP. Vault faithfully reads the token, validates it, dynamically maps the claims, and mints the OCI token.
*   **The Boundary Operator:** Identity Provider Administrators.

### Vault Runtime Identity Boundary (Self-Minted Mode)
When the plugin self-mints without an external JWT, it bases its trust entirely on the caller's Vault identity (e.g., `vault_entity_id`, aliases, and groups).
*   **The Architecture:** The plugin trusts the Vault core engine to verify *how* the workload authenticates to Vault. 
*   **The Boundary Operator:** The Vault Auth Method configuration.

### Transport and Caller Memory Boundary (The Returned Private Key)
When exchanging a token for `UPST`, the plugin has a convenience feature where it generates an RSA private/public keypair on the fly if the caller doesn't provide a `public_key`. OCI receives the public key, and Vault returns the `private_key` to the caller.
*   **The Architecture:** Once that `private_key` traverses the network and lands in the client's memory or on disk, it leaves the Vault security boundary entirely. 
*   **The Boundary Operator:** The Calling Client / Workload.

## 2. Attack Vectors & Mitigations

While the trust boundaries define the "locks on the doors", the attack vectors describe how an active adversary might try to pick those locks.

### A. Token Replay Attack
*   **The Attack:** An adversary intercepts a legitimate JWT as it travels from the user to Vault, or steals a recently used JWT from application logs, and attempts to exchange it again for a fresh OCI session token.
*   **The Mitigation:** In brokered mode, the plugin strictly evaluates `exp` (expiration), `nbf` (not before), and `iat` (issued at) claims. Furthermore, Vault operates over TLS, preventing in-transit interception. Upstream JWTs must be kept short-lived.

### B. Privilege Escalation via Upstream Claim Manipulation
*   **The Attack:** In Brokered Mode, the plugin uses `brokered_subject_token_claim_mappings` to map claims (like `department: {{ claims.department }}`). If an attacker finds a way to edit their own profile in the upstream IdP (e.g., Azure AD) and changes their department to `admin`, they can trick Vault into issuing a highly privileged OCI token.
*   **The Mitigation:** Vault administrators must ensure that mapped claims originate only from strictly controlled, non-user-editable fields in the upstream IdP. 

### C. The "Confused Deputy" (Stolen Vault Token)
*   **The Attack:** An attacker compromises a developer's machine and steals their active `~/.vault-token`. Since the developer has self-mint access via `oci/exchange/developer`, the attacker uses the stolen Vault token to self-mint OCI credentials, hoping to pivot into the cloud infrastructure.
*   **The Mitigation:** The blast radius is strictly contained. By mapping OCI trust to Vault's `vault_entity_id`, the attacker only gains the exact OCI permissions of the compromised developer. Vault administrators can quickly revoke the stolen Vault token, instantly severing the attacker's ability to generate new OCI sessions.

### D. JWKS Endpoint Spoofing / DNS Hijacking
*   **The Attack:** An attacker hijacks the DNS routing for the URL where the plugin's `jwks.json` is published, pointing OCI to a fake server hosting the attacker's public key.
*   **The Mitigation:** The JWKS endpoint must enforce strict HTTPS (HSTS) and rely on robust DNS infrastructure (e.g., DNSSEC) so OCI rejects the connection if the TLS certificate does not match the expected domain.

### E. Exposed Generated Private Key
*   **The Attack:** A client workload requests an OCI `UPST` without providing a public key. The plugin generates one and returns the private key. The workload writes this private key to a shared `/tmp` directory or exposes it in CI logs, where it is stolen by an attacker.
*   **The Mitigation:** Callers should ideally pre-generate their *own* key pairs securely in-memory, and pass only the `public_key` to Vault's `/exchange` endpoint. That way, the private key never traverses the network and Vault doesn't handle the private material for the session.
